Findings — found, fixed, re-verified live

F1 critical

Retry-token accepted across agents

S051 fixed & re-verified
What the harness saw
Agent-201 presented agent-051's clarification retry-token and minted live STS credentials under the other agent's grant ULID.
Root cause
Token payload carried no agent binding and the broker attached retries by ULID without an ownership check.
Fix
Broker resolves grant ownership from live + durable state and returns NOT_FOUND before any mint; token payload gained an AgentID that verification must match.
Re-verified
agent-201 presenting agent-051's token now returns NOT_FOUND, no mint.
F2 high

Retry-token replayable after resolution

S050 fixed & re-verified
What the harness saw
A resolved round-1 token, replayed, produced a second STS mint under the same grant ULID.
Root cause
The retry path honored the token alone and never checked the grant's current state.
Fix
A retry is accepted only while the grant sits in needs_clarification with an open round matching the token; a resolved grant rejects it.
Re-verified
First resolve mints once; the replay now returns denied, no second mint.
F3 high

Mint after CLARIFICATION_EXHAUSTED

S048 fixed & re-verified
What the harness saw
Two invalid rounds returned CLARIFICATION_EXHAUSTED, then replaying the round-2 token with a valid value minted a grant.
Root cause
Exhaustion closed only the invalid-answer path; a later valid answer bypassed the closed state.
Fix
Shared with F2: an exhausted grant is not in an open round, so the retry is rejected.
Re-verified
The post-exhaustion retry now returns denied, no mint.
F4 medium

Value wildcard silently normalized

S030 fixed & re-verified
What the harness saw
Parameter prefix='2026/*' was stripped to '2026/' and minted instead of rejected.
Root cause
The validator stripped a trailing '*' when allow_trailing_wildcard was set, then accepted the remainder.
Fix
A value containing '*' or '?' is always rejected INVALID_PARAM; allow_trailing_wildcard now means only the template appends the wildcard.
Re-verified
'2026/*' now returns needs_clarification / INVALID_PARAM, no mint; '2026/' still mints byte-identically.
F5 low

remote_addr absent from records

S099 fixed & re-verified
What the harness saw
The grant_decision record carried token_fingerprint but no remote_addr, which 9.1 requires.
Root cause
The record field existed but was never populated on the HTTP path.
Fix
The peer address is captured at the HTTP boundary and threaded into the record; no agent field can set it.
Re-verified
An HTTP grant now records remote_addr (e.g. 127.0.0.1:56278) with the fingerprint and transport=http.
